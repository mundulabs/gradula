# Gradula product and interface audit — 12 September 2026

Gradula has a useful purpose: coordinate people and coding agents around work, evidence and delivery. Its weakest point was that the interface demanded knowledge of its vocabulary while sometimes presenting unreliable signals as truth. A beautiful board cannot compensate for an edit that loses data or a report that reaches the wrong audience.

The intended hierarchy is now clearer: Board answers what needs work; a card explains the outcome, owner, evidence and history; Map explores relationships and time; Pulse summarizes measured activity; Channels controls delivery. Access belongs in its own settings tab.

## Verified problems and implemented fixes

| Problem | Change |
| --- | --- |
| Shared machine credentials could attribute Codex sessions to Claude Code. | Detect the active coder, pass session identity through CLI/MCP, retain the registered owner and machine. A configured Codex directory alone is not evidence of an active session. |
| Quarter-moon glyphs had inconsistent visual size; competing shape preferences obscured meaning. | Card notifications use five circles. Workflow progress uses squares for actual job steps, with explicit failure/status text. |
| Outside appeared to lose its selected template after saving through PostgreSQL. | Compare filter meaning independently of JSON object ordering and list ordering. Save/reopen checked in the browser. |
| A partial herald update reset omitted settings. | Merge existing values; preserve schedule consistently across memory and PostgreSQL. |
| Herald IDs could be edited/deleted across project boundaries. | Validate project ownership in the service and store, including database upserts. |
| Internal reports could be sent to public channels. | Reject manual public reports, omit public recipients, prevent public scheduling, skip legacy scheduled public reports. Paused channels cannot receive reports. |
| A card edit could overwrite a newer edit by another person. | Send only changed fields and atomically compare their original values before writing. Reject conflicts without a false chronicle entry. |
| Failed comments could erase their draft. | Clear only after successful mutation; use the returned card instead of making success depend on another read. |
| Late search/project responses could replace the current board. | Guard results by request sequence and project/filter scope; reset project-specific data. |
| Starting work could silently reopen review/done. | Require an explicit move back to Ready. |
| Startup failures could leave an empty loading surface. | Show loading/error states and a retry action. |
| Configured gates looked successful. | Remove the green treatment from mere gate presence. |
| Settings was an undifferentiated long sheet. | Channels, Reports and Access tabs; audience and active status; pause/resume; confirmation for removal/revocation. |
| Sheets lacked consistent focus containment and draft protection. | Shared native modal dialog, accessible title, scrolling content, Escape/backdrop protection and focus restoration when the opener remains available. New-card Cancel uses the same guarded close path. |
| Mobile controls were hidden and columns were awkward to navigate. | Persistent search, view switching and New card; stage tabs with counts; one readable column at a time. |
| Map could not scroll and its small dots were impractical touch targets. | Scrollable layout, keyboard-operable sectors, area selector, larger mobile labels and an equivalent tappable card list. |
| Pulse overflowed narrow screens and became stale while open. | Responsive grid, refresh every 30 seconds with overlap prevention, loading/error/retry states. |
| Visual hierarchy relied on tiny, low-contrast labels. | Higher contrast, larger card type, clearer primary actions, consistent spacing and shared sheet geometry; reduced-motion support. |

Workshop is the internal destination for pipeline updates; Outside remains for published updates. Pipeline messages update one stored message per workflow attempt, including after restart. Editing is preferred to deletion/reposting. Failed edits only permit replacement when Telegram explicitly says the original message is missing.

## Validation and limits

Automated checks cover both the memory store and a real local PostgreSQL database, plus TypeScript, production frontend build, surface/translations and documentation checks. Browser checks use synthetic local data at desktop and 390px mobile widths: board, settings, Outside save/reopen, reports, draft protection, Map scrolling and Pulse. No test message was sent to Telegram during this audit.

These changes have not been deployed. Real production OIDC, live Telegram editing and actual release jobs still need deployment validation. The pipeline polls recent GitHub workflow attempts; it is not a universal model of App Store review or deployment stages. It assumes one active scheduler instance. An ambiguous network failure after Telegram accepts a message can still cause a duplicate on retry.

This is a focused source and workflow audit, not a claim that every possible defect is eliminated. Larger boards, multiple simultaneous scheduler instances, native mobile screen readers and live integration failures need separate production-scale validation. The radial Map remains an exploratory view; the Board and mobile card list provide the direct route to work.
