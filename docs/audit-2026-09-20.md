# Gradula retrieval and history audit — 20 September 2026

Gradula has useful coordination machinery, but its original code graph was a
viewer with no agent retrieval path. It was not yet a knowledge system that
could reliably save coding tokens. This audit implements a working foundation;
it does not certify Graphify parity or state-of-the-art retrieval quality.

## History: preserve it

The 12 pre-existing GRD cards had 6–9 chronicle events each (89 events total).
Comparing verb, actor and event data found no repeated payloads. There was no
evidence-based reason to delete or rewrite history. The audit card is additional.
This is an inspection of these accessible records, not a global retention audit.

Keep the immutable chronology. Build small retrieval views from it; later add
linked decision summaries with source event IDs and explicit supersession.
Never rewrite an old decision as if the new one had always been true. A fresh
code scan should replace the derived index, not the cards or their evidence.

## Implemented retrieval

- One shared service behind `GET /api/v1/context`, `gradula context`, and
  `plan_context`; card query parameters are checked against the authenticated project.
- Path/scope-first lexical ranking, followed by one-hop relationships. Source-backed
  extracted edges sort before inferred/unreferenced edges. Incoming edges are included.
- Hard serialized UTF-8 response budgets, bounded nodes, explicit omitted counts,
  no automatic inclusion of the chronicle, and no model calls at query time.
- Source SHA, dirty flag, source lines and explicit freshness states. The client
  still checks its local edits and reads the actual source before changing it.
- A deterministic local publisher for Gradula's tracked JS/TS/Markdown. Real
  syntax parsing extracts declarations/imports; document citations connect to files.
  No claim of resolved call graphs, arbitrary document semantics or media support.

The board still stores one current bounded JSONB snapshot. This is suitable for
the present small graph; it is not an incremental, revision-partitioned graph store.
Query work currently scans the snapshot. The local scanner performs a full rebuild.

## Measurements and verification

A local scan of the staged implementation, before this report was indexed,
produced **738 nodes, 881 edges, 349,115 bytes**. It was explicitly dirty; the
revision identifies its base commit, not an immutable copy of uncommitted edits.

Seven exploratory queries looked for a predetermined relevant file among at most
eight returned nodes. Six hit: `normalizeGraph`, `reservation`, `pipeline`,
`contextOptions`, `codegraph`, and `gates`. `authentication` missed `src/auth.mjs`.
Responses were 587–4,495 bytes. The saved probe and graph are local audit artifacts,
not published production data. This small hand-selected probe is not a held-out
quality benchmark. Payload reduction against dumping a whole graph is not a
measurement of total token savings, latency or completed coding-task accuracy.

Tests exercise real CLI publishing, API authentication/validation, MCP calls,
cross-project isolation, UTF-8/escaping under budget, stale/missing/dirty source
metadata, history preservation, and AST extraction that ignores fake imports in
comments/strings. Graph and store contracts are also exercised against a temporary
real PostgreSQL instance. The complete suite passed **355 tests, zero skipped**
with PostgreSQL enabled. Documentation links and the patch whitespace check passed.
The implementation is prepared in `codex/GRD-69`; it has not been deployed.

## What would justify “Graphify or better”

1. **A reliable ingestion loop.** Initial scan per repository, incremental updates
   by content hash, deleted-file removal, generator/schema versions, branch-aware
   snapshots and visible coverage. Publish from clean CI/release source; never
   silently turn a failed scan into an apparently current graph.
2. **Deeper code understanding.** Resolve symbols/calls/import aliases with a
   language-aware indexer such as Graphify/tree-sitter or compiler/SCIP tooling.
   Integrate an existing indexer rather than rebuilding every language in Gradula.
3. **An evidence-connected knowledge graph.** Connect card → decision → document →
   symbol/file → test → commit → deployment. Preserve typed edges, source location,
   revision, extractor identity, confidence, and superseded/retracted claims.
   Keep observed behavior separate from inferred intent.
4. **Better retrieval, measured locally.** Combine exact/lexical search with graph
   traversal and evaluate semantic retrieval only where it improves recall. Add
   path/impact/explain queries and deterministic fallbacks to local source search.
5. **A real evaluation set.** At least 30 historical coding tasks, fixed source
   revisions and expected relevant files; compare local `rg`, this retrieval and
   Graphify using identical budgets. Measure file recall, irrelevant context,
   stale-source rate, prompt/completion tokens, latency and task correctness,
   including the amortized cost of building and refreshing the index.

Do not advertise “better” until that comparison supports it. A graph visualizer,
more nodes, or an aggressive context cutoff alone proves none of those outcomes.

## External technical basis

[Graphify's source and feature description](https://github.com/Graphify-Labs/graphify)
describe local AST extraction, typed/provenanced edges and query/path/explain tools.
These are useful comparison dimensions; its performance claims were not independently
reproduced here. Its hosted offerings and semantic model pass are separate choices.

[Anthropic's context-engineering guidance](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
supports retrieving small relevant context on demand. [Microsoft GraphRAG's query
overview](https://microsoft.github.io/graphrag/query/overview/) distinguishes local,
global and basic retrieval needs. Neither implies that global graph summarization
or model-generated indexing is the cheapest way to locate one code symbol.
